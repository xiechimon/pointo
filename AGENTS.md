# Pointo: Agent Instructions

Pointo is the human-to-agent half of a feedback loop: the agent builds, the human looks, points, talks and draws, and the agent understands what was meant and acts. A capture (`⌥⇧S` on macOS, a cabled iPhone (mirror plus native video), or ScrawlKit's three-finger long press inside an iOS app) records the screen, voice, cursor, clicks and `⇧` ink, and Pointo compiles it into a compact `.pointo` bundle (`contact-sheet.png`, `frames/frame-XX.png`, `summary.md`, `pointo.json`, `recording.mp4` or `recording.mov`, and `audio.wav`) in `~/Library/Application Support/pointo/captures/`. The Mac app is Rust + GPUI with a Swift helper (`pointo-helper`); ScrawlKit recordings are imported with `pointo import` (`Sources/ScrawlKit`). See README for the iPhone, ScrawlKit and testing.

## Principles

1. **The human's time is the scarce resource.** Starting (`⌥⇧S`), marking (`⇧`) and delivering (to the project folder, or `⌥⇧V`) should feel instant and take as few steps as possible.
2. **Don't make the agent guess what Pointo can capture.** When the OS, window server, Accessibility tree, browser page or host app knows which window, element, URL or project is on screen, record that fact instead of leaving the agent to infer it from pixels and words like "this part" or "here".
3. **Images stay visual and text carries meaning.** `contact-sheet.png` and `frames/*.png` show the screen, red ink, click ripples and each keyframe's number in a small white corner chip (no `#`, no time), with no rasterized captions or card chrome. `summary.md` and the clipboard carry the time-aligned transcript, interaction events and absolute file paths as plain text that pastes cleanly into a terminal or a GUI composer. Details are in `docs/keyframes-and-text.md`.
4. **Spend the agent's context where the signal is.** Cut keyframes only on real actions, marks or visual changes (never on speech pauses over a static screen), crop to the active region while keeping full frames on disk, and point the agent at `pointo zoom` for a closer look around a moment.
5. **Inspect real bundles after every change.** Whenever working on Pointo or after Kit tests a capture, inspect the latest bundles in `~/Library/Application Support/pointo/captures/` (both `summary.md` / `pointo.json` and visual `contact-sheet.png` / `frames/*.png` via `read`). Proactively surface concrete improvements whenever you spot issues in the output or UX, such as redundant or noisy text in `summary.md`, cluttered or low-density `contact-sheet.png` layouts, unnecessary keyframes (e.g. static frames cut on speech pauses), ghost strokes or misaligned annotations, slow startup or post-processing latency, or clipboard/paste friction.

## Build, test and install

- Keep `Cargo.toml` and `Cargo.lock` stable and build/test with `taskpolicy -c utility cargo build -j 3 --offline` and `taskpolicy -c utility cargo test -j 3 --offline -- --test-threads=2`.
- After changing Rust code, rebuild with `cargo build` before running `target/debug/pointo`: `cargo test` does not rebuild the binary.
- Keep everything local on `main` unless asked otherwise.
- **Experiments:** a change to what users get (the paste, `summary.md`, the images, routing) ships behind an experiment, off by default, until Kit turns it on for everyone. Kit enables one locally with `"experiments": {"<name>": true}` in `~/.config/pointo/config.json`; code asks `handoff::experiment("<name>")` (a value other than true/false, `"yes"`/`"off"` or a number is skipped and logged, and a bad value for any config key drops only that key) (tests see only `handoff::enable_experiment`, never the config file), and `pointo reprocess` / `pointo inspect` take `--experiment <name>` to try one on a bundle. Bug fixes ship normally. Current experiments are listed in `docs/keyframes-and-text.md`.
- **Feature map:** `docs/features.json` lists every user-facing feature with its status (`stable@<version>`, `main`, `experiment:<flag>`, `branch:<name>`, `review:#<pr>`), platforms, shortcuts, config keys and docs. A PR that adds, removes, renames or changes the status of a user-facing feature updates it in the same PR. A release moves its `main` entries to `stable@<version>` (`docs/release.md`). `cargo test feature_map` fails when a config key or experiment the code reads has no entry, or an entry names one that's gone. The site renders it at the unlinked `/map-tyyxsf5b/` (`MAP_DIR` in `site/scripts/feature-audit.ts`), with a status board and what looks inconsistent.
- **Always install and launch via `./scripts/install-app.sh` (`~/Applications/Pointo.app`)**: Never run `target/debug/pointo` directly as the background daemon because `hivemind clean` purges `target/` directories, which unlinks the binary on disk and causes macOS `tccd` to revoke Screen Recording and Microphone access. `./scripts/install-app.sh` copies the binary into `~/Applications/Pointo.app`, signs it with Kit's Developer ID (`dev.xiechimon.pointo`) so TCC permissions persist across rebuilds, and restarts the app.
- Agents: `install-app.sh` starts the app with `nohup` from your shell, and the agent's shell tool can kill it when the command returns. If `pgrep -fl Pointo.app` shows nothing afterwards, relaunch with `open -a ~/Applications/Pointo.app`.
- **Installing on another Mac (e.g. from the Studio onto the MacBook Pro):** run `./scripts/install-app-remote.sh pro`. Running `install-app.sh` over SSH can't sign (no keychain), and running it as a launchd job can't write into the installed app (App Management), so the remote script signs a staging copy in a launchd job and copies it into place over SSH.
  - **Releasing:** follow `docs/release.md` (version PR, `release-app.sh` with `SCRAWL_SPARKLE_DIR`, tag, the Pro's `dev.kit.pointo-appcast` job over `~/.local/share/pointo-release/updates`, appcast PR, site deploy from the Pro, Homebrew PR). Sparkle's tools and the updates folder live under `~/.local/share/pointo-release/`, never `target/` or `/tmp`.

## Safety and recovery

- Never `tccutil reset` Kit's real grants to test permissions (preview the permission panel instead; see `docs/onboarding-and-settings.md`).
- Test more than one display with a `CGVirtualDisplay` (`scripts/virtual-display.swift`), never on Kit's desk Mac.
- Never wake or flash Kit's displays: no `caffeinate -d`/`-u`, no real-screen recordings or benchmarks on the Studio (`perf/screen-guard.sh` refuses there). Use the MacBook Pro under `/tmp/pro-gui.lock`, a virtual display or a macvm VM.
- Never play audio out loud on Kit's Macs (`say`, `afplay`, speaker playback) to test the mic or transcription: feed recorded WAVs (`pointo reprocess <bundle> --out …` transcribes a bundle's `audio.wav` again), use a silent virtual loopback device you remove afterwards, or use the Mac mini VMs (`macvm`).
- Tests never write into a real project folder or Kit's config: swap the outside steps through `IngestHooks` (ScrawlKit ingest) and `routing::Hooks` (project routing), and deliver into a temp folder (`project::deliver`). `handoff::pinned_project`, `recent_projects` and `remember_project` see nothing and write nothing under `cfg(test)`.
- **Delivery recovery:** A capture's destination is a project folder (`pointo.json` `destination.project`; the copy lives in `<project>/.pointo/captures/`). Before re-sending a capture, read its `destination` and check whether the project's `.pointo/captures/<name>` already holds it (`pointo send` replaces that copy, so a second send is harmless, but it moves `.pointo/latest`). `pointo send` without `--project` uses the recorded destination, else the pinned project or what the page, port or terminal points at (`routing::project_for_send`). Preserve an explicit destination during recovery and ask before delivering to a different project. If no destination is recorded and the project is ambiguous, ask rather than guessing from the app's name or recent activity. An iPhone timeline's `session` is ignored. Never put `.pointo/` in a project's `.gitignore` or commit it: Pointo excludes it through `.git/info/exclude`.
